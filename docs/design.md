# תכנון ארכיטקטורה – פלטפורמת קליטה ועיבוד סקרים ב-GCP

**מסמך תכנון ארכיטקטוני | אזור ראשי: `me-west1` (תל אביב)**

## 1. מטרת הפתרון ועקרונות התכנון

הארגון מבקש להקים פלטפורמה לקליטת קובצי סקרים, בדיקת תקינותם, עיבודם והפקת דוחות. הפתרון כולל ממשק Web, שירות API מבוסס Python, שירות Worker לעיבוד ברקע, מסד נתונים PostgreSQL ואחסון קבצים.

הפתרון יתארח ב-GCP, תוך שימוש ב-GKE להרצת רכיבי האפליקציה וב-Cloud SQL for PostgreSQL לניהול הנתונים. Azure DevOps Server, המותקן בסביבה המקומית, יישאר מקור האמת לניהול הקוד ולתהליכי CI/CD. GitHub ישמש להגשת המטלה בלבד.

עקרונות התכנון:
- הפרדה בין Production ל-Non-Production, לרבות פרויקטים, הרשאות ונתונים.
- שמירת מסדי הנתונים והאחסון ללא חשיפה ציבורית.
- שימוש בזהויות שירות ובהרשאות מינימליות, ללא מפתחות Service Account ארוכי טווח.
- הפרדה בין קליטת קבצים, בדיקתם ועיבודם.
- המשך פעילות המערכת בעת ניתוק מהסביבה המקומית.
- עמידות בפני כשל Zone יחיד, לצד גיבוי ותכנון התאוששות מאסון.
- העדפת שירותים מנוהלים וצמצום מורכבות תפעולית, בהתאם ליכולת של צוות פלטפורמה קטן.

## 2. ארכיטקטורה ורכיבי הפתרון

המערכת תוקם בפרויקטים נפרדים עבור Production ו-Non-Production. רכיבי האפליקציה ירוצו ב-Regional GKE Cluster, בפריסה על פני שלושה אזורי זמינות ב-`me-west1`. הקלאסטר יוגדר עם Private Nodes, פיזור עומסים בין אזורים ו-Autoscaling.

### 2.1 תקשורת וזרימת המידע

משתמש חיצוני ניגש למערכת דרך External Application Load Balancer, המוגן באמצעות Cloud Armor. התעבורה מנותבת לשירותי Frontend ו-API באמצעות GKE Ingress.

ה־External Application Load Balancer מספק את נקודת הכניסה החיצונית למערכת, כולל ניתוב תעבורה והגנה באמצעות Cloud Armor. רכיב GKE Ingress משמש להגדרת חוקי הניתוב לשירותים בתוך אשכול GKE, ובארכיטקטורה זו הוא מנוהל באמצעות ה־GKE Ingress Controller, שמקים ומגדיר את ה־External Application Load Balancer ב־GCP. לכן אין מדובר בשני מאזני עומסים עצמאיים, אלא ברכיבים בעלי תפקידים משלימים.

שירות ה-API אחראי על אימות המשתמש מול ספק הזהויות הארגוני באמצעות OIDC/OAuth2, ועל בדיקת הרשאות בצד השרת בכל פעולה.

בעת העלאת קובץ, ה-API יוצר מזהה Submission ומנפיק Signed URL קצרת תוקף, המוגבלת לאובייקט ולפעולת ההעלאה הנדרשים. הקובץ מועלה ישירות ל-Cloud Storage, ללא מעבר דרך שירות ה-API. החתימה תתבצע באמצעות זהות שירות ייעודית, בהרשאות חתימה מתאימות.

הקבצים נקלטים באזור זמני (`Incoming`). תהליך בדיקה ייעודי בודק את סוג הקובץ ותוכנו, מבצע סריקת נוזקות ובדיקות תקינות. קובץ תקין מועבר לאזור המאושר (`Clean`), ורק לאחר השלמת הבדיקות נשלחת הודעה ל-Pub/Sub להפעלת תהליך העיבוד. קובץ חשוד או לא תקין מועבר ל-`Quarantine` ואינו ממשיך לעיבוד.

עם השלמת העלאת הקובץ ל-Cloud Storage, יופעל אירוע Object Finalized באמצעות Eventarc, שיניע את תהליך בדיקת הקובץ בשירות Validation. האירוע יוגדר עבור אזור Incoming בלבד, כדי למנוע הפעלות חוזרות בעקבות העברת קבצים בין אזורי האחסון.

שירות ה-Worker צורך הודעות מ-Pub/Sub, מעבד את הקבצים ושומר את תוצאות העיבוד ב-Cloud Storage. נתוני המטא-דאטה, סטטוס ההגשה ותוצאות העיבוד נשמרים ב-Cloud SQL. הורדת דוחות תתאפשר רק לאחר בדיקת הרשאות, באמצעות Signed URL קצרת תוקף.

### 2.2 רכיבי תשתית, אבטחה וגישה לנתונים

| רכיב | תפקיד |
|---|---|
| GKE | הרצת Frontend, API, Worker ותהליכי רקע |
| Cloud SQL for PostgreSQL | שמירת הגשות, סטטוסים ותוצאות |
| Cloud Storage | אחסון קבצים זמניים, מאושרים ודוחות |
| Pub/Sub | הפרדה בין קליטה לעיבוד אסינכרוני |
| Cloud Armor | הגנה על נקודת הכניסה הציבורית |
| Secret Manager | שמירת סודות ופרטי התחברות |
| Cloud Logging & Monitoring | איסוף לוגים, מדדים והתראות |

Cloud SQL יוגדר עם Regional High Availability וכתובת Private IP בלבד. הגישה אליו תתבצע מתוך רשת ה-VPC באמצעות Private Services Access. ה-Buckets יהיו פרטיים, עם Uniform Bucket-Level Access ו-Public Access Prevention.

תקשורת בין רכיבי המערכת תוגבל באמצעות כללי רשת והרשאות מתאימים. לכל רכיב תוגדר זהות נפרדת באמצעות Workload Identity for GKE, עם הרשאות מינימליות למשאבים הנדרשים לו. סודות יישמרו ב-Secret Manager ולא בקוד או בקובצי קונפיגורציה.

### 2.3 סנכרון נתוני ייחוס מהסביבה המקומית

תהליך סנכרון אופציונלי ירוץ כ-CronJob ב-GKE ויקרא נתוני ייחוס מ-SQL Server מקומי באמצעות חיבור HA VPN בין הרשת המקומית ל-VPC ב-GCP.

הסנכרון יתבצע מדי לילה באמצעות טעינת שינויים (Delta), על בסיס נקודת עדכון אחרונה. הנתונים ייטענו תחילה לאזור ביניים, יעברו בדיקות תקינות ורק לאחר מכן יעודכנו הנתונים הפעילים.

במקרה של ניתוק או כשל, המערכת תמשיך לקבל ולעבד סקרים באמצעות נתוני הייחוס התקינים האחרונים. לאחר חזרת הקישוריות יושלם הסנכרון החסר ללא יצירת כפילויות. יוגדרו ניטור והתראות על כשלי סנכרון ועל גיל הנתונים.

## 3. זמינות, אמינות והתאוששות

### 3.1 עמידות בפני כשל אזור זמינות (Zone)

Regional GKE Cluster יאפשר פיזור רכיבי האפליקציה בין אזורי זמינות שונים. יוגדרו פיזור Pods בין אזורים, מספר מופעים מתאים ו-Pod Disruption Budgets, לצמצום הפגיעה בשירות בעת כשל Zone יחיד.

Cloud SQL יוגדר ב-Regional HA, כך שבעת כשל באזור הזמינות הפעיל יתבצע מעבר למופע המתנה באזור אחר. האפליקציה תכלול מנגנוני Retry וחיבור מחדש למסד הנתונים, משום שהמעבר עשוי לגרום להפסקה זמנית בשירות.

### 3.2 עיבוד אמין של משימות

Pub/Sub מספק העברת הודעות במודל At-Least-Once, ולכן יש להביא בחשבון אפשרות לקבלת הודעה יותר מפעם אחת. ה-Worker יממש Idempotency על בסיס מזהה ההגשה וגרסת האובייקט ב-Cloud Storage, כדי למנוע עיבוד כפול.

ה-Worker יעדכן סטטוס עיבוד באופן מבוקר, ישתמש בניסיונות חוזרים עם השהיה מדורגת (Exponential Backoff), ויעביר הודעות שנכשלו שוב ושוב ל-Dead Letter Queue.

מנגנון Lease/Heartbeat ותהליך Reconciliation יסייעו באיתור משימות שנתקעו, בהחזרתן לעיבוד ובזיהוי פערים בין מצב הקובץ, סטטוס ההגשה ופרסום ההודעה ל-Pub/Sub. ניתן להשתמש ב-Outbox Pattern כדי לחזק את העקביות בין עדכון מסד הנתונים לפרסום אירוע העיבוד.

### 3.3 גיבוי והתאוששות מאסון (DR)

Cloud SQL יכלול גיבויים אוטומטיים ו-Point-in-Time Recovery. עבור קובצי Cloud Storage יוגדרו מדיניות שמירה, Soft Delete ו-Versioning בהתאם לצורך. יש לבצע בדיקות Restore תקופתיות ולא להסתפק בעצם קיומם של גיבויים.

לצורך התאוששות מאירוע אזורי נבחן אזור משני, `me-central2`. הבחירה בו תיבחן בהתאם להפרדה הגיאוגרפית מהאזור הראשי, לזמינות השירותים הנדרשים, לדרישות תושבות הנתונים ולמגבלות רגולטוריות.

שכפול נתונים לאזור נוסף, במיוחד כאשר מדובר במידע חסוי, יבוצע רק לאחר אישור גורמי אבטחת מידע, משפטיים ובעלי הנתונים.

בכפוף לאישור, ניתן להקים Cloud SQL Cross-Region Read Replica ולהעתיק את קובצי האחסון לאזור המשני באמצעות מנגנון שכפול או העתקה מתאים. תשתיות GKE והרשת יוקמו באזור זה באמצעות IaC.

תהליך ההתאוששות יכלול קידום מסד הנתונים, הפעלת השירותים, אימות שלמות וזמינות הנתונים ועדכון DNS. יש למנוע כתיבה במקביל בשני האזורים (Split Brain).

אם שכפול בין-אזורי לא יאושר, יש לתעד את מגבלת ההתאוששות האזורית ולקבל החלטה עסקית מפורשת לגבי הסיכון ויעדי ההתאוששות.

## 4. תהליך אספקה ותפעול (CI/CD)

Azure DevOps Server יישאר מקור האמת לניהול הקוד ולתהליכי CI/CD. ה-Agent יהיה Self-hosted Agent בסביבה המקומית וייזום תקשורת HTTPS יוצאת אל Azure DevOps Server. לא תידרש פתיחת חיבור נכנס מהענן לרשת המקומית.

תהליך האספקה יכלול:

1. פתיחת Pull Request, סקירת קוד ואישור מיזוג.
2. הרצת CI: בדיקות יחידה ואינטגרציה, בדיקות אבטחת קוד ותלויות וסריקת Image.
3. בניית Container Image והעלאתו ל-Artifact Registry באמצעות זהות Build ייעודית.
4. פריסה ל-Staging והרצת בדיקות תקינות מקצה לקצה.
5. קבלת אישור ידני לפני פריסה ל-Production.
6. פריסת אותו Image שנבדק ב-Staging, לפי Digest בלתי משתנה.

ה-Agent יזדהה מול GCP באמצעות Workload Identity Federation (WIF), ללא מפתח Service Account קבוע. לצורך פריסה ל-GKE הפרטי, ה-Agent יגיע ל-Control Plane באמצעות חיבור HA VPN, בכפוף להגדרת ניתוב, DNS וכללי Firewall מתאימים. תוגדר זהות Deploy נפרדת עם הרשאות פריסה בלבד.

יש לבצע הוכחת היתכנות לתמיכת גרסת Azure DevOps Server המותקנת בארגון ב-OIDC וב-WIF, ולוודא התאמה של Issuer, Audience ו-Claims. אם המנגנון אינו נתמך, תיבחר חלופת הזדהות מאושרת שאינה מבוססת על מפתח ארוך טווח.

במקרה של פריסה שנכשלה, תהליך השחרור יעצור ותתבצע חזרה לגרסת ה-Image הקודמת והתקינה. שינויי סכימה במסד הנתונים יתבצעו בגישת Expand/Contract, כדי לאפשר תאימות בין גרסאות במהלך הפריסה.

### ניטור ובקרת עלויות

Cloud Logging ו-Cloud Monitoring ישמשו לאיסוף לוגים, מדדים והתראות. הניטור יתמקד בזמינות ה-API, זמני תגובה, שגיאות, גיל הודעות בתור, הודעות ב-DLQ, עומס מסד הנתונים, כשלי Worker וגיל נתוני הסנכרון.

גורמי העלות העיקריים הם GKE, Cloud SQL בתצורת HA, אחסון קבצים, תעבורת רשת, שכפול בין אזורים ונפח הלוגים. צמצום העלויות יתבצע באמצעות Right-sizing, Autoscaling, מדיניות Lifecycle לאחסון, צמצום נפח הלוגים והגדרת Budgets והתראות תקציביות.

## 7. גבולות סביבה והנחות

הפתרון ייושם באמצעות הפרדה לפרויקטים:

- **Production:** שירותי המערכת, מסד הנתונים, אחסון הקבצים והודעות העיבוד של סביבת הייצור.
- **Non-Production:** סביבות פיתוח, בדיקות ו-Staging, עם נתונים סינתטיים והרשאות נפרדות. לא תתאפשר גישה לנתוני Production.
- **Shared Artifacts:** מאגר Artifact Registry משותף לתמונות האפליקציה, עם הרשאות כתיבה לזהות Build והרשאות קריאה לזהויות הפריסה.

הפתרון מניח שקיימת תשתית רשת ארגונית המאפשרת חיבור HA VPN ל-GCP, שספק הזהויות הארגוני תומך ב-OIDC ושניתן להעמיד Agent מקומי עבור Azure DevOps Server.

הפתרון הוא תכנון ארכיטקטוני בלבד ואינו כולל פריסה בפועל של משאבי GCP. זמינות השירותים באזור הנבחר, תאימות מנגנוני ההזדהות והפריסה, מנגנוני השכפול בין האזורים ויעדי RTO/RPO יידרשו לאימות במסגרת תכנון מפורט והוכחות היתכנות.
